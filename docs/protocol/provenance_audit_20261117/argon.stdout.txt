## 3. Recommended First Fix (Smallest Protective Change)

### Question: Is protecting `pull_results` alone enough, or must upload / producer overwrite guards be covered by the same change?
**Protecting `pull_results` alone is NOT enough.** Here is why:
1. If `pull_results` refuses to overwrite local files, but `modal_runner.py` (`run_gate`, `baseline_session`, `fast_session`) or `harness/gates.py` runs again on the Modal volume, **`run_gate` (`gdkit/gates.py:201,256`) and `_save()` (`harness/gates.py:108-111`) will immediately overwrite the remote receipt, log, and result files in place on the Modal volume**, destroying the remote evidence before `pull_results` is ever invoked.
2. Conversely, if `upload_repo` (`modal_runner.py:87`) runs with `batch_upload(force=True)`, it **pushes the local working tree over the Modal volume**, overwriting any unpulled or older remote artifacts in `runs/` (and uploading untracked/broken files like `harness/gates_optimized.py`).

### Minimal Boundary for Fix #1: "Three-Point Non-Destructive Artifact Guard"
Do **not** do a giant rewrite or redesign the directory schema yet. Implement one small, self-contained protective change across **two files** (`modal_runner.py` and `harness/gates.py`, plus a unit test file):

1. **Producer Guard in `harness/gates.py:main()` (around line 832, before `run_gate`):**
   - Before executing any gate, check if `run_dir / "receipts" / f"{gate.name}.json"` or `run_dir / "logs" / f"{gate.name}.log"` (or known output files for that gate) already exist on disk.
   - If any exist, **refuse to run** with exit code `1` (unless an explicit archive/attempt mechanism is later approved by the owner). This prevents `run_gate` and `_save` from ever clobbering an existing receipt, log, or result file locally or on Modal.
2. **Pull Guard in `modal_runner.py:pull_results()` (lines 123–141):**
   - Resolve `local_path` and assert `local_path.resolve().is_relative_to((repo_root / "runs").resolve())`.
   - Read remote bytes into memory and compute `remote_sha256`.
   - Classify each file:
     - **`NEW`** (`not local_path.exists()`): write atomically via temp file + `os.replace`.
     - **`IDENTICAL`** (`local_path.exists()` and `local_sha256 == remote_sha256`): skip write (`NO-OP`).
     - **`CONFLICT`** (`local_path.exists()` and `local_sha256 != remote_sha256`): **never overwrite `local_path`** (`ledger.jsonl` may only be updated if `remote_bytes.startswith(local_bytes)` and `gdkit.ledger.verify` passes on the temp file). Write conflicting remote bytes to a quarantined path outside `runs/` (e.g., `quarantine/<utc_ts>/<remote_path>`) and exit non-zero with a conflict report.
3. **Upload Guard in `modal_runner.py:upload_repo()` (lines 85–99):**
   - Exclude `runs/` from blind `force=True` overwrite: for any file under `runs/`, either skip uploading `receipts/`, `logs/`, `results/`, and `host.json` entirely (containers only need `ledger.jsonl`, `harness.json`, `run_scope.json`, `splits/`), or check remote sha256 first and abort on any conflict where remote bytes differ (or where local `ledger.jsonl` is not a verified prefix-extension of remote `ledger.jsonl`).

## 5. Preventable Future Loss vs. Historical Recovery Work

- **Preventable Future Loss (Solved by Software Guards):**
  - Overwriting an existing `receipts/<gate>.json`, `logs/<gate>.log`, `results/*`, or `host.json` during a rerun, container restart, `pull_results`, or `upload_repo`.
  - Executing monkey-patched helper code whose digest is invisible to `gate_code_hash`.
- **Historical Recovery Work (Cannot Be Solved by Hashes Alone):**
  - **What IS recoverable locally right now:** The original schema-0 `runs/20261110T135200Z-weightspace-abliteration-qwen3.5-0.8b/receipts/split_integrity.json` (`receipt_hash: 37d056fa...`) is intact in the Git object database (`HEAD:runs/.../receipts/split_integrity.json`) and in the external local backup ZIP (`resume-audit-20261117T121241131518Z.zip`), alongside the current schema-1 working copy (`039e93b1...`). Neither version should overwrite the other in place without an owner decision.
  - **What hashes CANNOT do:** SHA-256 hashes are one-way functions. The 8 earlier `host_provisioned` entries (`seq=16..25`) in the Qwen ledger record `input_hash` and `output_hash` for `host.json`, and `EXECUTION_LOG.md` describes Session 3's broken behavioral runs (`refusal_eval`, `judge_agreement`, `over_refusal_eval`), but **lost file bytes cannot be reconstructed from their hashes**. Unless those overwritten Session 3 files or earlier `host.json` snapshots survive in an external backup, local filesystem shadow copy, or uninspected volume snapshot, their full contents are permanently gone and must be documented honestly as overwritten historical artifacts rather than "repaired."
